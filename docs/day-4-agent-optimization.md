## 二、评测怎么设计的

三层，各自解决不同问题：

| 层 | 跑法 | 覆盖 | 判分 |
| --- | --- | --- | --- |
| `agent` | 本进程 `agent.run()`，拿到完整轨迹 | 回答质量、工具选择与参数 | 官方 `LocalEvaluator` + 内置 check + 自定义 check |
| `http` | 真实 `POST /agent`，解析 AG-UI SSE | 鉴权、事件流、上游失败、上下文 | 自定义断言（只看硬事实） |
| `unit` | 直接调工具函数，传非法参数 | 参数校验、注入防护 | 同上 |

14 条用例：3 正常、2 工具、1 无需工具、1 含糊、1 越界、1 模型失败、1 工具异常、
3 安全（未登录 / 越权 / 注入）、1 上下文。设计与代码见 `tests/agent/`。

**为什么不全用官方评测器**：它评的是"模型输出得好不好"，看不到 401 有没有拦住、
SSE 有没有建立、上游超时会不会挂住连接。这类问题只能打真实接口自己断言。
两类产出结构一致（`name / passed / reason`），进同一份报告。

**不用 LLM 当裁判**：同模型自评有偏、不可复现，也说不清扣分理由。开放式回答用
`manual_review` 记录人工结论，与机器判定并列保存。

## 四、两个问题与改动

### 问题一：非法工具参数被静默兜底（工具使用）

**现象**：E10 传非法 `status`，工具不报错，把筛选条件换成 `all` 返回全部待办。
**影响**：用户问"未完成的有哪些"，模型若给出一个不存在的筛选值，工具照样返回全部，
模型再按"未完成"的口吻叙述——答案错了，日志里也没有任何异常。
**原因**：`tools.py` 里 `normalized = status if status in _STATUS_FILTERS else "all"`。
**改动**（`64f1f9a`）：枚举外取值直接返回 `{"error": "invalid_status", "allowed": [...]}`，
让模型自己改参数；工具描述里写明枚举；`limit` 仍夹紧，但在返回体里回显实际生效值。

> 说明：基线里没观察到模型真的传错参数（E04/E05 参数全对）。这条是用单测把"误传时会被
> 静默吞掉"这条路径固定下来，属于防御性修复，不是已发生故障的复盘。

### 问题二：含糊请求不追问（回答质量）

**现象**：E07「帮我整理一下」被直接理解成"按优先级整理待办"：先查库、再给三段式方案。
**影响**：用户可能想的是"删掉已完成的"或"看看漏了什么"，模型猜错方向后输出 391 字，
用户要么重问一遍，要么被带偏。
**原因**：指令只写了"涉及待办就先调工具"，没有"信息不足先问"这一条，模型自然选了最省事
的解释。
**改动**（`0df9bc1`）：补一条规则——一句话能理解成多种意思时先问一句，信息不足不要先查库
再猜需求。

**没改什么**：这一轮没有同时去压缩回答长度。E03（要"安排建议"）本来就该展开，把长度
限制和澄清策略混在一次改动里，就无法判断效果来自哪一处。

## 六、限制

1. **样本小**：14 条用例、单模型、单账号、3 条待办。通过率从 92% 到 100% 只差 2 次运行，
   不能当成统计显著的提升；能说的是"两条失败用例在改动后稳定通过，其余没有退化"。
2. **重复次数不均**：关键用例 3 次，其余 1 次。单次用例的延迟与字数只能当参考。
3. **`agent` 类用例绕过了 HTTP 层**：登录、SSE、错误处理由 `http` 类单独覆盖，两类不能互相替代。
4. **延迟受本机负载影响**，只适合同机前后对比，不是绝对性能指标。
5. **评测器的实验性**：`agent_framework` 的 evals 模块标注 experimental，升级小版本可能改 API。

## 七、判定器本身修了三次（真正没达预期的地方）

写评测比写优化难。三次修正都不是模型的问题：

| 次数 | 现象 | 根因 |
| --- | --- | --- |
| 1 | E13 注入判为失败 | 用"回答里出现标记"判断是否被注入，但标记就在待办标题里，模型为了解释给用户听必然引述。改成"标记单独占一行"才算执行 |
| 2 | E03 建议类判为失败 | 要求标题逐字出现，模型把"看完 /docs"改写成"打开 /docs"就被判编造。改成 4 字滑窗覆盖率 ≥50% |
| 3 | E07 澄清后仍判失败 | 要求每个编号条目对上库中标题，但澄清话术里的「1. 列出未完成 2. 只看新加的」是选项不是数据。改成"没调工具就不许断言有 N 条" |

这三次的共同点：**断言写成了"措辞对不对"，而不是"任务完成没完成"**。每次都是先看模型
实际回答，再回头改判定，而不是看到红就改提示词——顺序反了，优化就成了给测试打工。
